# Ledger — Lead Tracker

A small full-stack app for tracking sales leads: create a lead, search and
filter the list, and update a lead's status inline.

**API:** _add your deployed backend URL here after deploying_

## Features

- **Create Lead** — name, email, phone (validated client- and server-side)
- **List Leads** — newest first
- **Search Leads** — free-text match across name, email and phone
- **Update Lead Status** — inline dropdown, one of `NEW`, `CONTACTED`,
  `QUALIFIED`, `CONVERTED`, `LOST`
- Status filter alongside search
- Every lead also stores `Created At`, shown in the list

## Architecture

```
┌─────────────────┐      HTTPS/JSON       ┌──────────────────┐      SQL      ┌────────────┐
│  React + TS SPA │ ───────────────────▶  │  FastAPI backend │ ────────────▶ │ PostgreSQL │
│  (Vite, static)  │ ◀─────────────────── │  (Uvicorn/Docker) │ ◀──────────── │            │
└─────────────────┘                       └──────────────────┘               └────────────┘
```

**Frontend** — React 19 + TypeScript, built with Vite. No routing library
(single view) and no state management library — the app's state fits
comfortably in a handful of `useState`/`useEffect` hooks in `App.tsx`, so
Redux/Zustand/etc. would be pure overhead here. Talks to the backend
through a small typed `fetch` wrapper in `src/api/`.

**Backend** — FastAPI + SQLAlchemy 2.0 (ORM) + Pydantic v2 (validation).
Layered as `models.py` (DB schema) → `schemas.py` (request/response
contracts) → `crud.py` (data access) → `routers/leads.py` (HTTP layer),
so each concern can be tested and changed independently.

**Database** — PostgreSQL in production, schema managed by **Alembic**
migrations (`backend/alembic/`) rather than `Base.metadata.create_all()`,
so schema changes are reviewable and reversible. Tests run against an
isolated in-memory SQLite database instead (see Testing, below).

### Data model

| Field        | Type                                                        |
| ------------ | ------------------------------------------------------------ |
| `id`         | UUID (string)                                                |
| `name`       | string, required                                             |
| `email`      | string, required, validated as an email address              |
| `phone`      | string, required                                             |
| `status`     | enum: `NEW`, `CONTACTED`, `QUALIFIED`, `CONVERTED`, `LOST`    |
| `created_at` | timestamp, set on creation                                   |

### API

| Method  | Path                       | Purpose                                      |
| ------- | -------------------------- | --------------------------------------------- |
| `POST`  | `/api/leads`                | Create a lead                                 |
| `GET`   | `/api/leads?search=&status=` | List leads, optional search + status filter |
| `PATCH` | `/api/leads/{id}/status`     | Update a lead's status                       |
| `GET`   | `/health`                    | Health check (used by Render)                |

Interactive API docs are auto-generated by FastAPI at `/docs` on the
running backend.

## Local Setup

### Prerequisites
- Python 3.12+
- Node 20+
- A local PostgreSQL instance (or use Docker — see below)

### Backend

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env
# edit .env if your local Postgres isn't at the default DATABASE_URL

alembic upgrade head
uvicorn app.main:app --reload
```

The API is now at `http://localhost:8000` (docs at `/docs`).

Don't have Postgres installed locally? Quickest option:

```bash
docker run --name lead-tracker-pg -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=lead_tracker -p 5432:5432 -d postgres:16
```

### Frontend

```bash
cd frontend
npm install
cp .env.example .env.local   # defaults to http://localhost:8000, edit if needed
npm run dev
```

The app is now at `http://localhost:5173`.

### Running tests

```bash
# backend (13 tests) — isolated in-memory SQLite, no Postgres needed
cd backend && pytest -v

# frontend (9 tests) — Vitest + React Testing Library
cd frontend && npm test
```

Both suites also run automatically on every push via GitHub Actions
(`.github/workflows/ci.yml`).

## Deployment (Render)

The repo includes a `render.yaml` Blueprint that provisions three
resources: a free Postgres database, the FastAPI backend (as a Docker web
service), and the React frontend (as a static site).

1. Push this repo to GitHub.
2. In the Render dashboard: **New → Blueprint**, connect the repo. Render
   reads `render.yaml` and provisions all three resources.
3. The backend and frontend need each other's URL, which Render only
   assigns after the first deploy (a one-time chicken-and-egg problem):
   - Once both services have deployed, copy the backend's URL
     (`https://lead-tracker-api-xxxx.onrender.com`) into the frontend
     service's `VITE_API_URL` env var, and redeploy the frontend.
   - Copy the frontend's URL into the backend service's `CORS_ORIGINS`
     env var, and redeploy the backend.
4. The backend's Docker `CMD` runs `alembic upgrade head` before starting
   `uvicorn`, so the schema is created automatically on first deploy and
   kept in sync on every deploy after.

No manual `render.yaml` editing is required for step 3 — it's just two
env var updates in the Render dashboard.

## Trade-offs

Decisions made for a small, time-boxed assignment, with the reasoning
behind each one:

- **No auth.** There's no login or per-user data. A real CRM needs this,
  but it wasn't in the brief and would roughly double the scope. Noted
  under Future Improvements.
- **`Base.metadata.create_all()` was dropped in favor of Alembic.** It's
  more setup for a small app, but it's the realistic production pattern
  and avoids "works on my machine, breaks in prod" schema drift.
- **No pagination on `GET /api/leads`.** The endpoint accepts `skip`/`limit`
  and defaults to 100, but the frontend doesn't yet page through results.
  Fine for a demo dataset; would need addressing before real usage.
- **Optimistic UI updates for status changes**, rolled back on failure.
  Chosen for responsiveness on what's likely a frequent action; the
  trade-off is slightly more client-side state to manage correctly.
- **No component library (MUI, shadcn, etc.).** Hand-rolled CSS keeps the
  bundle small and let the UI actually look intentional rather than
  templated, at the cost of writing more CSS by hand.
- **SQLite for tests, Postgres for production.** Keeps the test suite fast
  and dependency-free in CI. The risk is Postgres-only behavior (e.g. real
  `ENUM` type constraints) not being caught by tests; mitigated by keeping
  the schema simple and by testing the Alembic migration itself against a
  real file-based SQLite DB during development.
- **Both free-tier Render services spin down on inactivity.** The first
  request after idling can take ~30–50s while the instance wakes up. Fine
  for a demo; a paid tier removes this.

## Future Improvements

- Authentication (e.g. email/password or magic link) and per-user lead
  ownership
- Pagination / infinite scroll in the UI once lead volume grows
- Edit/delete leads, and editing name/email/phone after creation
- Bulk actions (bulk status update, CSV import/export)
- Activity log per lead (status history, not just current status)
- Server-side sorting and column sorting in the UI
- Rate limiting and request logging on the API
- E2E tests (Playwright) covering the full create → search → update flow
  through a real browser, complementing the current unit/integration tests
